## User Requirements
用户希望在没有自有服务器和域名的情况下，以低成本或零成本方式把当前项目部署到公网。已确认选择免费 PaaS 组合：前端使用 Cloudflare Pages，后端和数据库使用 Railway 免费额度。

## Product Overview
本方案将现有前后端分离项目拆开部署：前端构建为静态站点托管在 Cloudflare Pages，后端 FastAPI 与 MySQL 托管在 Railway。通过公网地址可访问登录页、业务表格、角色用户菜单管理和主题配置等功能。

## Core Features
- 使用免费域名和免费额度完成公网访问，不购买服务器。
- 前端静态资源由 Cloudflare Pages 全球 CDN 托管。
- 后端与 MySQL 部署在同一 Railway 项目内，降低配置复杂度。
- 支持登录、单位筛选、用户增删改查、菜单数据加载和主题配置持久化。
- 明确免费层限制：国内访问速度不稳定、服务休眠冷启动、平台免费政策可能变化。

## Tech Stack Selection
- 前端托管：Cloudflare Pages，免费静态站点托管，输出目录为 `dist`。
- 后端托管：Railway Python 服务，运行 FastAPI，使用平台注入的 `PORT`。
- 数据库：Railway MySQL。PlanetScale 已取消免费层，因此不再作为免费数据库方案。
- 代码托管：GitHub 仓库，供 Cloudflare Pages 与 Railway 自动拉取部署。
- 项目技术：Vue 3、TypeScript、Vite 5、Element Plus、FastAPI、SQLAlchemy、aiomysql、MySQL。
- 浏览器验证：使用 `playwright-cli` 检查公网页面加载、登录和基础数据展示。

## Implementation Approach
采用“最小代码改造加平台配置”的方式完成部署，不引入新的前后端架构。

核心策略：
1. 前端保持 Vite 构建流程不变，生产环境通过 `VITE_API_URL` 指向 Railway 后端完整地址。
2. 后端沿用现有 FastAPI 代码，仅调整数据库初始化逻辑，避免在 Railway MySQL 上执行无权限的建库语句。
3. Railway 同时提供 MySQL 与 Python 服务，后端通过环境变量读取数据库连接信息和 JWT 配置。
4. CORS 设置为 Cloudflare Pages 域名，避免通配来源带来的安全风险。
5. 项目使用 hash 路由，Cloudflare Pages 静态托管无需额外 SPA rewrite 配置。

关键决策与理由：
- 选择 Railway MySQL 而不是 PlanetScale：Railway 更契合当前 `mysql+aiomysql` 技术栈，且免费额度足以容纳演示数据。
- 选择 Cloudflare Pages 而不是 Vercel：Cloudflare Pages 免费流量额度更宽松，静态资源分发稳定。
- 不在代码中硬编码 Railwa y 地址：Railway 应用域名需部署后才知道，推荐在 Cloudflare Pages 构建环境变量中配置 `VITE_API_URL`。
- 不改动本地开发代理：`.env.development` 和 `vite.config.ts` 的 `/api` 代理仍服务于本地和内网穿透场景，应保持不动。

性能与可靠性：
- 静态页面由 Cloudflare CDN 承载，前端性能瓶颈较小。
- Railway 免费服务在长时间无访问后可能休眠，首次请求会有冷启动延迟。
- 数据库连接池已有 `pool_pre_ping=True`，可减少连接失效带来的错误。
- 免费额度有限，需在 Railway 控制台监控用量。

## Implementation Notes
- 部署前必须把 `JWT_SECRET` 改为随机强字符串，禁止继续使用默认值。
- Railway MySQL 会自动创建数据库，用户通常没有执行 `CREATE DATABASE` 的权限，因此需修改 `server/app/database.py` 的 `init_db()`。
- Cloudflare Pages 的 `VITE_API_URL` 是构建期变量，修改后必须重新构建和部署前端。
- 后端 `CORS_ORIGINS` 应填写实际 Cloudflare Pages 域名，例如 `https://xxx.pages.dev`。
- 本地现有内网穿透、前后端服务和 MySQL 不应停止或覆盖，避免影响当前演示地址。
- 数据库数据默认不迁移：Railway MySQL 为空库，首次启动由 `init_db` 建表并由 `seed_database` 导入初始账号和菜单数据。如需保留当前本机业务数据，需单独导出导入。
- 所有密码、JWT 密钥、数据库连接串只能通过平台环境变量配置，不能提交到仓库。

## Architecture Design
部署后的访问链路：

1. 用户访问 Cloudflare Pages 公网域名。
2. Cloudflare Pages 返回前端静态资源。
3. 浏览器调用 `VITE_API_URL` 指向的 Railway 后端接口。
4. Railway FastAPI 服务连接 Railway MySQL，完成登录、CRUD 和主题配置读写。
5. 后端返回 JSON，前端渲染页面。

本项目适合该架构的原因：
- 前端是纯静态构建产物，天然适合 Cloudflare Pages。
- 项目使用 hash 路由，不需要服务器 history fallback。
- 后端为单进程 FastAPI，无需复杂容器编排即可部署到 Railway。
- 数据库使用标准 MySQL 驱动，Railway MySQL 可直接兼容。

## Key Code Structures
后端数据库初始化需改为兼容平台托管 MySQL：

```python
async def init_db():
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
```

Cloudflare Pages 构建环境变量：

```text
VITE_API_URL = https://xxx.up.railway.app/api
```

Railway 后端环境变量映射：

```text
DB_HOST = Railway MySQL Host
DB_PORT = Railway MySQL Port
DB_USER = Railway MySQL User
DB_PASSWORD = Railway MySQL Password
DB_NAME = Railway MySQL Database
DB_CHARSET = utf8mb4
JWT_SECRET = 随机强字符串
JWT_ALGORITHM = HS256
JWT_EXPIRE_SECONDS = 86400
CORS_ORIGINS = https://xxx.pages.dev
```
